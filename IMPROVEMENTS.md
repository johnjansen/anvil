## Category: Code Quality

### CQ-1: `logCmd` and `taskLogCmd` are near-identical duplicates
**Files:** `cmd/anvil/main.go:421-486` and `main.go:717-781`
**Description:** Both functions resolve a todo name to a session ID, then either print or follow the log. The only difference is the usage string. This 60-line block is duplicated verbatim.
**Suggested approach:** Extract a `resolveAndShowLog(args []string, commandName string)` helper and call it from both.
**Priority:** P2

### CQ-2: `watchCmd` and `projectCreateCmd` duplicate watch-file creation
**Files:** `cmd/anvil/main.go:161-220` and `main.go:887-942`
**Description:** Both functions independently marshal a `watchFrontmatter`, create the hash directory, and write the timestamped `.md` file. The logic is ~50 lines duplicated.
**Suggested approach:** Extract a `registerWatch(absPath string) error` helper used by both.
**Priority:** P2

### CQ-3: `watchFrontmatter` is defined twice
**Files:** `cmd/anvil/main.go:1462-1465` and `internal/daemon/daemon.go:578-580`
**Description:** The daemon's copy omits `WatchedAt`; main's copy includes it. Both parse the same files. This is a classic sign that the parsing logic should live in one place (e.g., `internal/config` or a new `internal/watch` package).
**Priority:** P2

### CQ-4: `loadWatchedPaths` (daemon) and `loadAllWatched` (main) duplicate frontmatter-scanning logic
**Files:** `internal/daemon/daemon.go:533-576` and `cmd/anvil/main.go:1472-1530`
**Description:** Both functions walk `~/.anvil/watched/`, sort directory entries descending, find the latest `.md` file, and parse YAML frontmatter to extract the project path. The scanner logic is ~40 lines and appears twice.
**Suggested approach:** Move to `internal/config` as `LoadWatchedProjects() ([]WatchEntry, error)`.
**Priority:** P2

### CQ-5: Deprecated `Config.Runner` used in daemon startup log
**Files:** `internal/daemon/daemon.go:99`
**Description:**
```go
dlog.Startup(d.config.TickInterval.String(), d.config.Runner, poolSize)
```
`d.config.Runner` is the deprecated single-runner field. When a user configures only `runners:` (the current recommended field), the startup message prints an empty string as the runner name.
**Suggested approach:** Use `strings.Join(d.config.Runners, ", ")` in the log call.
**Priority:** P1

### CQ-6: Manual argument parsing throughout main.go
**Files:** `cmd/anvil/main.go` (all command functions)
**Description:** Every command hand-rolls `for i := 0; i < len(args)` flag parsing. This produces subtle inconsistencies: some errors use `log.Fatal`, others use `fmt.Fprintf(os.Stderr) + os.Exit(1)`. Mixed exit paths are confusing and hard to test.
**Suggested approach:** Use `flag.FlagSet` per command, or adopt a lightweight library like `pflag`. This also enables `--help` per subcommand automatically.
**Priority:** P2

### CQ-7: `addCmd` is a trivial one-liner alias
**Files:** `cmd/anvil/main.go:313-315`
```go
func addCmd(args []string) {
    taskCreateCmd(args)
}
```
**Description:** Not harmful, but the CLI surface has two entry points (`anvil add` and `anvil task create`) that behave identically. This means bug fixes in one don't automatically apply to the other, and the help text must be kept in sync manually.
**Priority:** P3

### CQ-8: `newUUID` and `newRunID` generate different ID formats
**Files:** `internal/project/project.go:227-233` and `internal/daemon/daemon.go:527-531`
**Description:** `newUUID` sets the version (0x40) and variant (0x80) bits per RFC 4122 but formats with non-standard hex widths. `newRunID` generates a different format entirely (8-4-4-4-12 with different byte slices). Neither is standard UUID v4. Having two ID-generation functions with different formats makes debugging harder.
**Suggested approach:** Use `github.com/google/uuid` or consolidate on one internal function in a shared package.
**Priority:** P3

### CQ-9: `cron.setToSlice` returns unsorted results non-deterministically
**Files:** `internal/cron/parser.go:209-216`
**Description:** `setToSlice` iterates a `map[int]bool` whose iteration order is undefined in Go. The comment says "Sort not needed for display", but the `Parser.String()` output would be non-deterministic across runs, making log diffing or test assertions unreliable.
**Suggested approach:** Add `sort.Ints(result)` before returning.
**Priority:** P2

### CQ-10: `SessionPath` is deprecated but still called from daemon
**Files:** `internal/project/project.go:239-241`, `internal/daemon/daemon.go:517`
**Description:** `SessionPath` has a `Deprecated` godoc comment and just delegates to `SessionPathBySessionID`, but `daemon.go:taskLogLink` calls it with a `sessionID` argument (not a task ID). The naming is confusing — `SessionPath(projectPath, todoID)` but calling it with a session ID works by accident because the function just passes through.
**Suggested approach:** Call `SessionPathBySessionID` directly and remove `SessionPath`.
**Priority:** P3

## Category: Architecture

### AR-1: `main.go` is a 1531-line god file
**Files:** `cmd/anvil/main.go`
**Description:** All CLI command logic, argument parsing, the `followLog` tail implementation, the multiplex log streamer, watch-file helpers, and the `projectHash`/`loadAllWatched` utilities live in a single file. This makes unit testing impossible without importing the entire binary, diffs are unreadable, and any refactoring risks unintended side effects.
**Suggested approach:** Move each command group into its own file or package: `cmd/anvil/cmd_task.go`, `cmd/anvil/cmd_project.go`, `cmd/anvil/cmd_logs.go`, with shared utilities in `cmd/anvil/helpers.go`. Or adopt a proper command pattern with a `Command` interface.
**Priority:** P1

### AR-2: No test suite
**Files:** entire codebase
**Description:** There are zero `_test.go` files. The cron parser (`Parse`, `Matches`, `Next`), project loading (`LoadTodos`, `AddTodo`, `WriteRunRecord`), config loading, `slugify`, `shellEscape`, and `cleanEnv` are all untested despite being core correctness-critical paths.
**Suggested approach:**
- `internal/cron/parser_test.go`: table-driven tests for all supported syntax variants and edge cases
- `internal/project/project_test.go`: use `t.TempDir()` for filesystem tests
- `internal/runner/runner_test.go`: mock runner command with `echo`
- `internal/config/config_test.go`: test YAML parsing and backwards-compat paths
**Priority:** P0

### AR-3: `project.Load` does no validation
**Files:** `internal/project/project.go:51-54`
```go
func Load(path string) (*Project, error) {
    return &Project{Path: path}, nil
}
```
**Description:** `Load` accepts any path and always succeeds. Errors about missing `.anvil/` directory surface much later in `LoadTodos` or `AddTodo` with confusing messages. CLI commands like `listCmd` call `project.Load` and only discover the project isn't initialized when `LoadTodos` fails.
**Suggested approach:** Have `Load` verify that `.anvil/todos/` exists and return a descriptive `ErrNotAnvilProject` if not.
**Priority:** P2

### AR-4: Daemon watch-file format is shared state parsed by two packages
**Files:** `internal/daemon/daemon.go:578-596`, `cmd/anvil/main.go:1462-1530`
**Description:** The watched project registry (`~/.anvil/watched/`) is written by `main.go` and read by both `main.go` and `daemon.go`. Both packages hand-parse the YAML frontmatter independently. If the format ever changes, both parsers must be updated in sync.
**Suggested approach:** Move all watch registry logic (read/write/list) into `internal/config` or a new `internal/watch` package.
**Priority:** P2

### AR-5: No daemon single-instance guard
**Files:** `internal/daemon/daemon.go:271-273`
```go
os.Remove(d.socketPath)
listener, err := net.Listen("unix", d.socketPath)
```
**Description:** When `anvil serve` starts, it unconditionally removes any existing socket file before binding. If a daemon is already running, the second `anvil serve` silently deletes the first daemon's socket, making it unreachable via `anvil ps`/`kill`/`logs` — while both daemon processes continue running and processing tasks independently. This can cause tasks to run twice simultaneously.
**Suggested approach:** Write a PID file at `~/.anvil/daemon.pid`. On startup, check if the PID file exists and if the PID is alive; if so, exit with an error message. Remove the PID file on clean shutdown.
**Priority:** P1

## Category: Robustness

### RO-1: Daemon reports its own PID until child process starts
**Files:** `internal/daemon/daemon.go:167-233`
**Description:**
```go
d.tasks[taskKey] = &RunningTask{
    ...
    PID: os.Getpid(),  // ← daemon's PID, not the child's
    ...
}
// ... runner.Run() starts the child and calls onStart(childPID) asynchronously
```
Between when the task is added to `d.tasks` and when `onStart` fires, `GET /ps` returns `d.tasks[taskKey].PID = os.Getpid()` — the daemon's own PID. Any client that tries to send a signal to that PID would kill the daemon itself.
**Suggested approach:** Initialize `PID: 0` and document that 0 means "starting". Only report the PID once `onStart` has been called.
**Priority:** P1

### RO-2: `followLog` infinite-loops when `taskName` is empty
**Files:** `cmd/anvil/main.go:1190-1211`
```go
if !taskRunning && taskName != "" {
    fmt.Println("[task completed]")
    return
}
```
**Description:** The exit condition for "task completed" is gated on `taskName != ""`. If `taskName` is empty (e.g., when a UUID is passed directly to `anvil log`), the function will continue polling forever even after the task finishes. The only exit path becomes SIGINT.
**Suggested approach:** Either always require `taskName` to be set, or add a secondary exit condition based on file growth stalling independently of `taskName`.
**Priority:** P1

### RO-3: `handleKill` substring matching is too broad
**Files:** `internal/daemon/daemon.go:359`
```go
if task.TaskID == req.ID || task.Name == req.ID || strings.Contains(task.Name, req.ID) || task.Project == req.ID {
```
**Description:** `strings.Contains(task.Name, req.ID)` means sending `{"id": "a"}` could match and kill any task whose name contains the letter "a". In a multi-project setup with many running tasks, this is a silent footgun.
**Suggested approach:** Remove the `strings.Contains` clause. Match only on exact `TaskID` or exact `Name` (full path). The CLI already resolves names to IDs before sending the request.
**Priority:** P1

### RO-4: Work queue silently drops tasks when full
**Files:** `internal/daemon/daemon.go:488-496`
```go
select {
case d.workQueue <- workItem{project: pt.proj, todo: pt.todo}:
    dispatched++
default:
    dlog.Warn("work queue full, dropping %s/%s", projName, pt.todo.Name)
    d.inFlightMu.Lock()
    delete(d.inFlight, taskKey)
    d.inFlightMu.Unlock()
}
```
**Description:** When the queue is full, tasks are dropped. For recurring tasks, the next tick will redispatch them, so the impact is one missed run. For one-shot tasks, a missed enqueue means the task is deleted from disk but never actually executed on the next success — actually no, it is re-evaluated each tick. But the user sees no indication that their one-shot task was temporarily dropped.
**Suggested approach:** Log a warning that is visible to the user via `anvil ps` or `anvil logs`. Consider a retry queue for one-shot tasks specifically. The queue size (`poolSize*4`) could also be made configurable.
**Priority:** P2

### RO-5: `cron.Matches` silently returns `false` on invalid expressions
**Files:** `internal/cron/parser.go:200-206`, `internal/daemon/daemon.go:445`
**Description:** The daemon calls `cron.Matches(t.Schedule, thisMinute)` which swallows parse errors and returns `false`. A todo with an invalid schedule like `"0 9 * * Mon"` (named weekday instead of 0-6) will never execute and the user gets no warning.
**Suggested approach:** Pre-validate schedules in `project.AddTodo` and reject invalid expressions at creation time. In the daemon tick, add a `dlog.Warn` when a todo's schedule cannot be parsed.
**Priority:** P2

### RO-6: `taskKillCmd` and `taskRmCmd` send different ID types to `SendKillRequest`
**Files:** `cmd/anvil/main.go:856` and `main.go:812`
```go
// taskKillCmd:
daemon.SendKillRequest(todo.ID)   // sends task UUID
// taskRmCmd:
daemon.SendKillRequest(todo.Name) // sends filename like "check-issues.md"
```
**Description:** The two kill paths send different identifier types. `handleKill` handles both via its multi-condition match, but the inconsistency means the match semantics differ silently. If the `strings.Contains` clause is removed (per RO-3), `taskRmCmd`'s kill would need to also send `todo.ID`.
**Priority:** P1

### RO-7: Daemon shutdown does not drain running tasks
**Files:** `internal/daemon/daemon.go:114-128`
```go
case <-d.stop:
    ...
    close(d.workQueue) // signals workers to drain and exit
    workerWg.Wait()
```
**Description:** `close(d.workQueue)` stops new tasks from being dispatched. Workers drain the queue and exit. But tasks currently executing inside `d.runner.Run()` are not cancelled — they run until their own timeout. There's no graceful drain signal to in-progress tasks. If the daemon receives SIGTERM, it will return from `d.Stop()` while child processes are still running.
**Suggested approach:** On shutdown, cancel all in-flight task contexts before waiting for workers. Store a map of `cancel` functions (already present in `RunningTask.Cancel`) and call each on shutdown.
**Priority:** P1

### RO-8: `logsMultiplex` line buffer grows unboundedly
**Files:** `cmd/anvil/main.go:1391-1393`
```go
n, readErr := s.file.Read(buf)
if n > 0 {
    s.buf = append(s.buf, buf[:n]...)
```
**Description:** If a task emits a very long line without a newline character (e.g., a base64-encoded blob), `s.buf` grows until the task completes. With many tasks, this could exhaust memory.
**Suggested approach:** Add a max line buffer size (e.g., 1MB). If exceeded, flush the partial buffer with a `[line truncated]` marker.
**Priority:** P2

### RO-9: `projectHash` uses only 4 bytes of SHA-256
**Files:** `cmd/anvil/main.go:1467-1470`
```go
func projectHash(absPath string) string {
    h := sha256.Sum256([]byte(absPath))
    return fmt.Sprintf("%x", h[:4])
}
```
**Description:** Only 8 hex characters (32 bits) are used. The collision probability for two distinct project paths is ~1 in 4 billion. While vanishingly small in practice, a collision would cause one project's watch entry to be silently reused for another. Using more bytes (e.g., 8) costs nothing.
**Suggested approach:** Use `h[:8]` for 16 hex characters.
**Priority:** P3

## Category: Performance

### PE-1: `loadWatchedPaths` reads all watch files on every daemon tick
**Files:** `internal/daemon/daemon.go:533-576`
**Description:** On every tick (default: every 10 seconds), the daemon scans `~/.anvil/watched/`, reads and parses a YAML file per watched project. With 50 watched projects this is 50 file reads every 10 seconds.
**Suggested approach:** Cache the result with a timestamp. Invalidate only when a watch directory's mtime changes (poll with `os.Lstat`), or use `fsnotify` to watch for changes to `~/.anvil/watched/`.
**Priority:** P3

### PE-2: `cron.Next()` is O(minutes × years) but is never used
**Files:** `internal/cron/parser.go:168-185`
**Description:** `Next()` iterates minute-by-minute for up to 5 years to find the next match. For an expression like `0 0 29 2 *` (leap day), it would iterate ~525,600 minutes/year × 5 years = ~2.6 million iterations. Since `Next()` is not called anywhere in the codebase, this is dead code. If it ever gets used (e.g., for showing "next run time"), a smarter algorithm should be implemented.
**Suggested approach:** Either remove `Next()` if unused, or implement a field-skipping algorithm (advance to next valid hour/day instead of stepping minute-by-minute).
**Priority:** P3

### PE-3: `followLog` busy-polls at 500ms
**Files:** `cmd/anvil/main.go:1172-1212`
**Description:** The log-following loop unconditionally sleeps 500ms between reads. This adds up to 500ms of latency for each chunk of output. On macOS and Linux, OS-level file watching (`kqueue`/`inotify`) would eliminate this lag and reduce CPU usage.
**Suggested approach:** Use `gopkg.in/fsnotify/fsnotify` for change notification with a 500ms fallback timeout.
**Priority:** P3

## Category: Security

### SE-1: Session ID appended to shell command without quoting
**Files:** `internal/runner/runner.go:85-94`
```go
cmdStr += " --resume " + sessionID
// ...
cmd := exec.CommandContext(ctx, "sh", "-c", cmdStr+" "+escaped)
```
**Description:** `sessionID` is a hex string today (safe), but it is appended directly to the shell command string without quoting. If the session ID format ever changes to include characters meaningful to the shell, this would be exploitable. The same applies to `freshID` on the else branch.
**Suggested approach:** Either quote the session ID with `shellEscape(sessionID)`, or — better — pass the session ID as a separate argument via `exec.Command` rather than building a shell string.
**Priority:** P2

### SE-2: `lockPath` includes the full path from user input
**Files:** `internal/daemon/daemon.go:213-215`
```go
lockPath := t.Path + ".lock"
if err := os.WriteFile(lockPath, []byte(fmt.Sprintf("%d\n", os.Getpid())), 0600); err != nil {
```
**Description:** `t.Path` comes from reading `~/.anvil/todos/` directories. If a symlink or directory traversal were placed there by a malicious actor, `t.Path + ".lock"` could write a file outside the `.anvil/` tree. In a single-user setup this is low risk, but worth hardening.
**Suggested approach:** Validate that `t.Path` is within the expected `<project>/.anvil/todos/` subtree before writing the lock file.
**Priority:** P3

### SE-3: Embedded skills are written to `.claude/` unconditionally, overwriting existing files
**Files:** `internal/project/project.go:160-183`
```go
return os.WriteFile(target, data, 0644)
```
**Description:** `writeEmbeddedFS` overwrites any existing file at the destination path without checking for local modifications. If a user customized their `.claude/skills/anvil/SKILL.md`, re-running `anvil init` or `anvil watch` would silently overwrite their changes.
**Suggested approach:** Check if the file exists and is identical before overwriting. Alternatively, only write if the file doesn't exist, and document that users should use a separate path for customizations.
**Priority:** P2

## Category: Observability

### OB-1: Log files accumulate indefinitely
**Files:** `internal/daemon/daemon.go:225-226`, `internal/runner/runner.go:67-79`
**Description:** Each task run writes a new `.log` file to `<project>/.anvil/logs/<task-id>/`. A task running every minute generates 1440 log files per day, per task. There is no rotation, pruning, or size limit. On long-lived projects, this directory will grow without bound.
**Suggested approach:** Add a `log_retention` config option (e.g., keep last N runs, or delete logs older than N days). Run cleanup at daemon startup and periodically during the tick loop.
**Priority:** P1

### OB-2: Run records accumulate indefinitely
**Files:** `internal/project/project.go:267-286`
**Description:** Each task dispatch writes a JSON file to `<project>/.anvil/runs/<task-id>/`. Like log files, these accumulate without bound for recurring tasks.
**Suggested approach:** Same log retention mechanism as OB-1. Keep the last N run records per task (e.g., 100).
**Priority:** P2

### OB-3: No structured/machine-readable log mode
**Files:** `internal/daemon/logger.go`
**Description:** All daemon output is human-readable colored text. There is no JSON log mode for piping to log aggregators (Datadog, Loki, etc.), or for scripting against daemon output.
**Suggested approach:** Add a `log_format: json` config option that switches `dlog` to emit JSON lines with `ts`, `level`, `msg`, and structured fields.
**Priority:** P3

### OB-4: Tick heartbeat is noisy but lacks useful signal
**Files:** `internal/daemon/daemon.go:410-424`
**Description:** On every non-cron tick (every 10 seconds by default), the daemon logs either "idle" or lists running tasks. For a daemon with no work, this produces 6 idle log lines per minute. For production use this is very chatty without adding value.
**Suggested approach:** Make the heartbeat interval configurable separately from the tick interval, or only log idle heartbeats at DEBUG level (or suppress them entirely after N consecutive idle ticks).
**Priority:** P3

### OB-5: No exit code tracking in RunRecord
**Files:** `internal/project/project.go:40-48`, `internal/daemon/daemon.go:246-255`
**Description:** `RunRecord` stores `RunID`, `TaskID`, `SessionID`, `PID`, and `Started` but not whether the task succeeded or failed, the exit code, or the error message. `anvil task get` shows "idle/running" but there's no way to see "last run failed with exit code 1".
**Suggested approach:** Add `ExitCode int`, `Error string`, and `Finished time.Time` to `RunRecord`.
**Priority:** P1

## Category: Developer Experience

### DX-1: `anvil task ls` status check uses wrong key format
**Files:** `cmd/anvil/main.go:647-650`
```go
taskKey := fmt.Sprintf("%s/%s", p.path, t.Name)
status := "idle"
if _, ok := runningByID[taskKey]; ok {
    status = "running"
}
```
**Vs `runningByID` populated at line 594:**
```go
runningByID[fmt.Sprintf("%s/%s", t.Project, t.Name)] = t
```
**Description:** `runningByID` is keyed by `<project-path>/<task-name>` using `t.Project` (which is the project's absolute path from `RunningTask.Project`). The lookup uses `<p.path>/<t.Name>` where `p.path` is also the absolute project path — this appears to match. However, `RunningTask.Name` is set from `t.Name` (the filename like `check-issues.md`) at line 169, while `t.Project` is `proj.Path`. The keys should match, but this should be verified with a test.
**Priority:** P2 (needs test coverage to verify)

### DX-2: `anvil log` and `anvil task log` have redundant error messages
**Files:** `cmd/anvil/main.go:465-466`
```go
fmt.Fprintf(os.Stderr, "no session log found (looked at %s): %v\n", project.SessionPath(abs, id), err)
```
**Description:** The error includes the path from `project.SessionPath(abs, id)` which is the _old deprecated_ path function, not the actual `sessionPath` that was resolved. When a user sees this error, the "looked at" path is incorrect.
**Suggested approach:** Use `sessionPath` (already resolved on the next line) in the error message instead.
**Priority:** P1

### DX-3: No `anvil kill <name>` top-level shortcut
**Files:** `cmd/anvil/main.go:32-69`
**Description:** To kill a running task, the user must type `anvil task kill <name>`. There is no `anvil kill <name>` convenience alias, despite `anvil add`, `anvil list`, `anvil get`, `anvil delete`, and `anvil log` all existing as top-level shortcuts for their `task` counterparts.
**Suggested approach:** Add `case "kill": killCmd(os.Args[2:])` to the main switch.
**Priority:** P2

### DX-4: Help text for `anvil log` is inconsistent with actual behavior
**Files:** `cmd/anvil/main.go:434` and `main.go:729`
**Description:** The usage string shows `usage: anvil log [-f] <name|uuid>` but the function actually resolves `name` to a UUID and then resolves it again via `LatestSessionID`. The "uuid" part in the usage is misleading — passing a raw UUID only works if the todo has no `Name` match and the UUID happens to be the todo's `ID` field, which it never is directly (the session ID comes from `LatestSessionID`).
**Priority:** P2

### DX-5: `anvil add` with `--schedule ""` is not obvious
**Files:** `cmd/anvil/main.go:538-543`, `README.md`
**Description:** Creating a one-shot task requires passing an empty string as the schedule argument: `anvil add -s "" "do something"`. This is not discoverable. The README documents it but many users will miss it.
**Suggested approach:** Add a dedicated `--once` flag to `anvil add` and `anvil task create` that sets the schedule to empty.
**Priority:** P2

### DX-6: `anvil ps` column widths are hardcoded and truncate on common values
**Files:** `cmd/anvil/main.go:288-299`
```go
fmt.Printf("%-30s %-20s %-10s %-10s %s\n", "PROJECT", "TASK", "PID", "ELAPSED", "STARTED")
```
**Description:** PROJECT is truncated at 30 characters and TASK at 20. A typical project path like `/Users/username/code/my-project` (31 chars) gets truncated to `/Users/username/code/my-projec...`. TASK names derived from long task descriptions also routinely exceed 20 chars.
**Suggested approach:** Compute column widths dynamically based on the actual data, with reasonable minimums.
**Priority:** P2

### DX-7: `MaxConcurrent` is parsed but never enforced
**Files:** `internal/project/project.go:37`, `internal/daemon/daemon.go:476`
**Description:** The `max_concurrent` frontmatter field is fully parsed into `Todo.MaxConcurrent`, documented in the spec, but the scheduler never checks it. The current `inFlight` guard only allows exactly 1 concurrent run per task, regardless of the configured value. Users who set `max_concurrent: 2` get no benefit.
**Suggested approach:** In `tick()`, when checking `d.inFlight`, count how many running tasks match the `taskKey` prefix and compare to `t.MaxConcurrent` (defaulting to 1 if 0).
**Priority:** P1

## Category: Missing Features

### MF-1: No daemon restart/reload command
**Description:** There is no `anvil reload` or signal-based config reload. To change `max_workers` or add a new runner, the user must `kill <daemon-pid>` and restart manually. A `SIGHUP` handler that reloads `~/.anvil/config.yaml` without dropping in-flight tasks would significantly improve operator experience.
**Priority:** P2

### MF-2: No `anvil task pause`/`anvil task unpause`
**Description:** There is no way to temporarily disable a recurring task without deleting it. Users must delete and recreate the task to achieve this.
**Suggested approach:** Add a `paused: true` flag to todo frontmatter. The scheduler skips paused todos. Add `anvil task pause <name>` / `anvil task unpause <name>` commands that toggle the flag.
**Priority:** P2

### MF-3: No log retention configuration
**Description:** See OB-1/OB-2. As a standalone missing feature: there is no `log_retention_days` or `max_runs_per_task` config option. Long-running deployments will fill disk.
**Priority:** P1

### MF-4: `anvil ps --watch` / live refresh
**Description:** `anvil ps` is a one-shot snapshot. There's no equivalent of `watch anvil ps` that refreshes the table in-place. Given that tasks can run for minutes, a live view is useful.
**Suggested approach:** Add `-w`/`--watch` flag to `anvil ps` that clears and redraws the table every 2 seconds.
**Priority:** P3

### MF-5: No `--dry-run` for `anvil serve`
**Description:** There's no way to see what tasks would be dispatched on the next tick without actually running them. Useful for debugging cron expressions.
**Suggested approach:** `anvil serve --dry-run` runs one tick, logs what would be dispatched, and exits.
**Priority:** P3

### MF-6: No `anvil task history <name>`
**Description:** Run records are persisted to disk but there's no CLI command to view them. The user can't see "this task ran 5 times; runs 1-3 succeeded, run 4 failed".
**Suggested approach:** Add `anvil task history <name>` that reads all run records in `.anvil/runs/<task-id>/` and displays them in a table.
**Priority:** P2

### MF-7: No `--validate` for cron expressions
**Description:** `anvil add -s "0 9 * * Mon"` silently creates a task with an invalid schedule (named weekdays not supported). The task is never dispatched and the user gets no feedback.
**Suggested approach:** Validate the schedule in `AddTodo` using `cron.Parse()` and return an error for invalid expressions.
**Priority:** P1
